# 実装計画書 - サブスク管理アプリ（仮）
> 作成: 2026-08-19 / MVP完成条件: 本番環境（Vercel Production）にデプロイした状態で、契約中の全サブスクの登録・通知・自動繰り越し・エクスポートが一気通貫で動作すること（一般公開は対象外）

---

## 前提・方針

- **根拠文書**: `requirements.md`（v1.1）、`design.md`（2026-08-01時点）
- **タスク粒度**: 30分〜4時間で完了できる単位に分解
- **担当区分**:
  - 🤖 AI担当: コード生成、設定ファイル、ロジック実装
  - 👤 人間担当: 外部サービスのアカウント作成・秘密情報の入力・実機での受信/動作確認
  - 🤝 協働: AIが実装しUI調整や確認を人間が行うタスク
- **テスト方針**: design.mdは`lib/date.ts`のみテスト対象と明記しているが、`lib/billing.ts`（月額換算・繰り越し・月末アンカー処理）も設計書自身が「事故が起きやすい箇所」と明記しているため単体テストを追加する。それ以外はMVPでは動作確認のみ
- **UI方針**: design.mdに記載がなかったため、Tailwind CSS + shadcn/uiを採用（フォーム・モーダルが多いため実装速度を優先）
- **タスクID**: `T{フェーズ番号}-{連番}` の形式（例: T0-1）。フェーズ番号はdesign.mdの11章の実装順序に沿った連番（0〜10）

## Phase 1: 認証基盤（DBスキーマ＋RLS＋画面）

> `user_id`が全テーブルに絡むため、後付けは全クエリの手戻りになる（design.mdの3章）。DBスキーマとRLSを最初に固める。

### T1-1: DBスキーマ＋RLS実装 ⏱3.5時間 🤖AI
**作業内容**:
- design.mdの4章の通りに5テーブル（`subscriptions`, `cards`, `payment_history`, `notification_logs`, `settings`）を作成するマイグレーションSQLを作成（ユニーク制約・外部キー・`ON DELETE SET NULL`含む）
- 全テーブルでRLSを有効化しデフォルト拒否、`auth.uid() = user_id`ポリシーを設定
- `lib/supabase/server.ts`（Cookie経由・RLS前提）と`lib/supabase/admin.ts`（service_role・cron専用）を実装

**依存**: T0-4完了後

### T1-2: ログイン・新規登録・パスワード再設定画面 ⏱4時間 🤖AI
**作業内容**:
- `/auth/login`：メール・パスワード入力、Supabase Auth標準サインイン（F-11）
- `/auth/signup`：Supabase Auth標準サインアップ（自作検証ロジックなし）
- パスワード再設定：Supabase組み込みフローを画面に組み込み

**依存**: T0-4, T0-3完了後

### T1-3: 認証フロー動作確認 ⏱1時間 👤人間
**作業内容**:
- サインアップ→ログイン→ログアウト→パスワード再設定を一通り確認
- 別アカウントでログインし、RLSにより他人のデータが見えないことを確認

**依存**: T1-1, T1-2完了後

## Phase 5: 日次バッチ：繰り越し・通知・履歴記録

> 最も事故が起きやすい中核ロジック（design.mdの6章）。冪等性とテストを重視する。

### T5-1: 繰り越しロジック＋単体テスト ⏱5時間 🤖AI
**作業内容**:
- `lib/billing.ts`に繰り越しロジックを追加：`while (next_billing_date < today)`で冪等に実装、`billing_anchor_day`による月末問題対応（例：1/31→2/28→3/31）、`yearly`は日付ライブラリに委任（自前計算しない）
- 月末問題・うるう年・複数周期分の追いつきをケースとした単体テスト（今回の追加決定事項）
- `payment_history`への記録、繰り越し時の`is_trial`解除

**依存**: T2-1完了後

### T5-2: 通知抽出・送信ロジック ⏱4.5時間 🤖AI
**作業内容**:
- 通知対象抽出：`settings.notify_days`の各Nについて「残りN日以内・`notification_logs`未記録」のものを抽出（design.mdの6章）
- メール本文テンプレート（件名1件/複数件、本文、同日複数件の集約仕様、design.mdの7章）
- Resend送信処理。送信成功時のみ`notification_logs`に記録（失敗時は翌日の追いつきに委ねる、design.mdの13章）

**依存**: T1-1完了後

### T5-3: 日次バッチAPI + Cron設定 ⏱3時間 🤝協働
**作業内容**:
- 🤖 `/api/cron/daily`：`CRON_SECRET`によるヘッダー検証、繰り越し→通知抽出→送信を統合、サブスク1件ごとのtry/catchで異常データが他件に影響しないようにする
- 🤖 `vercel.json`に`0 23 * * *`（UTC）を設定
- 👤 Vercelダッシュボードでcronが有効化されていることを確認

**依存**: T5-1, T5-2完了後

### T5-4: バッチ動作の通し確認 ⏱1.5時間 👤人間
